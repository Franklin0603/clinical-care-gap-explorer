01

What this project actually does

A person with type 2 diabetes is supposed to get a blood test called an A1c roughly every six months. It measures average blood sugar over the previous three months. If that number drifts upward and nobody notices, the damage lands on kidneys, eyes and nerves — slowly, and then all at once.

Sometimes nobody notices. The patient moves, changes doctors, misses an appointment, or simply falls off a list. Twelve months pass with no A1c on file.

That is a care gap: a patient who qualifies for a routine piece of care and hasn't received it. This project finds them.

The query itself is easy. Diabetic patients with no A1c in twelve months is about four lines of SQL. The project is not really about the query.

02

Why it's really a data quality project

A care-gap list gets handed to a nurse who picks up a phone. So a wrong list costs something in both directions.

  • False positiveA wasted call to someone who already had the test — their result was filed under a duplicate record, or with a broken link back to the patient.
  • False negativeWorse. The patient stays invisible, and everyone trusts the report that hid them.

Real clinical data arrives with duplicate rows, lab values in the wrong units, patients registered twice under different record numbers, and timestamps that contradict each other. A care-gap report built on unvalidated data is worse than no report, because people act on it.

So the build order is: load the raw data, deliberately break it, catch the breakage, measure what fraction was caught — and only then report the gaps. The quality work is the project.

03

Codes, and why nothing is stored as words

Healthcare does not store "diabetes" as text. It stores a number drawn from an agreed vocabulary.

Free text does not survive contact with reality. One system writes Diabetes mellitus type 2, another DM Type II, a third T2DM, a fourth NIDDM — a term abandoned in the 1990s. All four mean the same thing and no WHERE description = … will ever match them all. Worse, a display string can be quietly reworded by a vendor during a routine upgrade, and your report breaks without erroring.

A code is stable, unambiguous and international. Join on codes. Never join on display names.

This project uses SNOMED, LOINC and RxNorm. The billing systems are claims-side and out of scope.

04

A LOINC code is a question, not an answer

4548-4 means precisely one thing: the proportion of hemoglobin that is glycated, in blood. The result value and its unit are stored separately, in their own columns.

That separation is exactly where unit errors live. An A1c is reported in percent — around 5 is normal, 9 is poorly controlled. Blood glucose is reported in mg/dL, where normal is around 90. Put a mg/dL value into a percent field and you get an A1c of 250: biologically impossible, and yet a perfectly valid number as far as the database is concerned. No type system catches it. Only a range check does.

05

Where "twelve months" comes from

HEDIS is a set of quality measures published by NCQA. Health plans are scored against them, and real money moves based on the score. The relevant one here is the diabetes care measure set.

This matters for exactly one reason: the thresholds in this project are not invented. Diabetic patients need an A1c within twelve months is a published measure with a formal definition of who counts. Using the real rule instead of a plausible-sounding one is the difference between a care-gap report and a demo.

Stated plainly in the app The genuine HEDIS specification is far stricter than what's implemented here — precise enrolment requirements, exclusion criteria, hospice carve-outs. This project implements the idea, not the certified measure, and says so on the page rather than in a footnote.

Terms you'll hit in the repo

A1c HbA1c · LOINC 4548-4
Blood test giving average blood sugar over roughly three months, reported in percent. Under 5.7 is normal, 5.7–6.4 prediabetes, 6.5 and above diabetes.
Care gap
A patient eligible for a routine piece of care who hasn't received it.
Cohort
The set of patients a measure applies to. Here: people with diabetes. Get it wrong and everything downstream is wrong, which is why it lives in one file with every code written out explicitly.
Encounter
One interaction with the health system — a visit, an admission, a phone consult. Most clinical data hangs off an encounter.
MRN medical record number
The ID a hospital assigns a patient. Local to that organisation, which is why one human can hold several — and why duplicate-patient detection is a real problem rather than a contrived one.
Observation
One recorded measurement: a lab result, a blood pressure, a height. Carries a LOINC code, a value, and a unit.
PHI protected health information
Identifiable patient data, legally protected under HIPAA in the US. This project uses synthetic data only — Synthea generates fictional people — so no PHI is ever involved.
Value set
The list of codes that defines a measure's population. Published measures use lists of dozens rather than single codes, for the reason finding 1 demonstrates.
Bronze / Silver / Gold
A data-engineering convention, not a clinical term. Bronze is raw as-loaded, Silver is typed and validated, Gold is the reporting tables. The value is being able to show what the data looked like before anyone touched it.

What profiling this data turned up

Four findings, each of which changed a decision that had already been written down — which is the argument for profiling before building rather than after.

  • 439Prediabetes is not diabetes. A text search for "diabet" matches it, and it is the largest group. Those patients do not qualify for the measure; including them roughly triples the denominator.
  • 73One diabetes code is not enough. These patients carry a complication of diabetes with no diagnosis code on file. Anchoring on the obvious code drops 45% of the cohort, and the sicker half.
  • 951The A1c range in the spec was wrong. Clean values below the proposed floor of 3.0 — an 11% false-positive rate before any defect was injected.
  • 0Diabetes is never resolved. Of 835 diabetes condition rows, none has an end date. The cohort needs no "still active" filter, which removes a whole class of date logic.

Each is written up with its reasoning in the decision records, and asserted in the test suite so a later change has to be deliberate.
