Clinical Care Gap Explorer

How it fits together

Five stages, thirteen seconds, and one assertion that has to hold every time.

Synthea → DuckDB → Bronze → Silver → Gold → a static site
Synthetic data only. No real patient information.

The layers

Bronze A photocopy

Every column loaded as text, nothing cast, deduped or filtered. The only additions are a load timestamp and the source filename. Loading as text is deliberate — let the loader infer types and it will quietly null whatever does not fit. A third of observations here carry text results, so inference would be a coin flip about which rows survive.

Silver Typed and validated

Six checks run against Bronze. Surviving rows are cast to real types; rejected rows land in quarantine with a reason attached, never dropped.

Gold The answer

One row per diabetic patient, sourced from Silver only. If Gold ever read Bronze, the entire validation layer would be decorative.

The guarantee

bronze rows = silver rows + quarantined rows

Asserted for every table, on every run. The pipeline stops when it fails.

This is the difference between "nothing is silently dropped" as a claim in a README and as a property somebody can check. A row leaves the pipeline in exactly two ways: it reaches Silver, or it sits in quarantine with a reason. Any third way is a silent drop — the failure this project exists to prevent.

Why the data is broken on purpose

Stage two damages 249 rows in six realistic ways and logs exactly what it damaged.

Without that log, a catch rate is a claim — "I found twelve problems" says nothing about whether that was twelve of twelve or twelve of four hundred. With it, the checks are scored against a known answer: 6 of 6 defect types, 249 of 249 rows, each caught by the check meant for it.

A defect found by the wrong check is a coincidence, not a working check, and the score counts it as a miss.

What it is not

Five stages running in thirteen seconds on one machine. There is no scheduler, no partitioning, no incremental load, and adding any of them at this size would be ceremony rather than engineering.

What would change at scale — orchestration with real retries, checks as a dbt or Great Expectations suite, alerting on drift rather than absolute counts, partitioning by load date, a replayable quarantine — is written up with its trade-offs in the data quality reference. Each entry names what this build actually ran into rather than listing tools.
